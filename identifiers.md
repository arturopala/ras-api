# Relief at Source API – Business Identifiers

This document lists every business and technical identifier the service handles: where it comes from, where it goes, and how it is validated. Validation rules are compared across three sources:

- **Local**: checks in this repository (readers, regexes, equality checks).
- **Library**: checks inside dependencies, e.g. `domain-play` wrapper types with a `require`. `domain-play-30` 13.0.0 is on the classpath, but **none of its types (`Nino`, `PsaId`, …) are imported in `app/`**, so no library-level identifier validation applies. The local `models.Nino` is a plain case class with no checks.
- **Contract**: patterns in the bundled OpenAPI specs `resources/public/api/conf/1.0/application.yaml` and `2.0/application.yaml`. No DES or Upscan schema is bundled.

**Terminology**: one value, the pension scheme organisation's enrolment identifier, has several names in the code. It is called `userId`, `id`, `uid`, `userIdentifier` (in audit events), `userid` (in the remove route) and `pensionSchemeOrganisationID` (in the DES payload). Likewise, the Upscan **`reference`** is also called `fileId`, `fileName`, `name` and `filename` (GridFS).

## 1. Party/tax identifiers – NINO

**Lifecycle**:
- Issued by HMRC (DWP/HMRC NINO allocation).
- Supplied by the scheme administrator for each lookup, as JSON for the API or as CSV column 1 for bulk.
- Never stored by this service, except inside the echoed input row of the results CSV in GridFS, which expires by TTL.
- Not returned in the API response.

**Sources**: untrusted only (request body or CSV). It is never compared with any authenticated identity, which is correct: the caller is an organisation acting on behalf of members.

**Transformations** (`IndividualDetails.individualDetailsReadsWith`):
1. Validate `value.toUpperCase` against the regex. The stored value keeps its original case until step 3.
2. `padTo(9, " ")`: an 8-character NINO without a suffix becomes 9 characters with a trailing space.
3. `toUpperCase`.

**Uses**:
- DES request body field `nino`.
- Audit events: `ReliefAtSourceResidency` (`nino`) and `ReliefAtSourceAudit_DES_Response` (`nino`).
- The bulk results CSV, which echoes the original input text, not the normalised value.
- It is deliberately left out of log messages.

**Rule comparison**:

| Aspect | Local | Library | Contract v2 | Contract v1 |
|---|---|---|---|---|
| Prefix exclusions | Same as the contract | — (not used) | `BG GB KN NK NT TN ZZ`, D/F/I/Q/U/V first, D/F/I/O/Q/U/V second | same |
| Suffix | Optional `[A-D]` | — | Optional | **Required** |
| Case | Insensitive (upper-cased before matching) | — | Upper case only | Upper case only |
| Spaces | Rejected | — | Rejected | Rejected |

⚠️ **Mismatches:**
- Locally, v1 requests without a suffix are accepted, although the v1 contract requires one.
- Lower-case NINOs are accepted locally but are outside both contracts. They are upper-cased before being sent, so this does no harm.
- The DES-side format is not documented in this repository. The padded trailing space for suffix-less NINOs assumes that DES accepts a 9-character NINO padded with a space.

Format example: two letters, six digits and an optional suffix letter, e.g. `QQ123456C` or `QQ123456`.

## 2. User/enrolment identifiers – pension scheme organisation ID

**Issuer**: HMRC enrolment store. It is the first identifier value of one of these enrolments:

| Enrolment key | Holder |
|---|---|
| `HMRC-PSA-ORG` | Pension Scheme Administrator (PSAID) |
| `HMRC-PP-ORG` | Pension Practitioner (PPID) |
| `HMRC-PODS-ORG` | PSA registered via the Pension Scheme Online Digital Service |
| `HMRC-PODSPP-ORG` | Pension Scheme Practitioner via the Pension Scheme Online Digital Service |

**Trusted source**: the `authorisedEnrolments` retrieval. It is derived in two different ways:

- `controllers.getEnrolmentIdentifier`, used by Lookup and File: filters the enrolments to the four keys, then takes `.head` of the identifiers of the first one.
- `FileSessionController.isAuthorised`: `enrolments.enrolments.head.identifiers.head.value`, with no key filter.

⚠️ **Observation:** both derivations pick the "first" element of a `Set`. For a user who holds more than one pension enrolment, the chosen ID is arbitrary and may differ between endpoints. In that case the file-session ownership check can fail, or a session can be keyed under a different ID from the one used for the results file.

**Untrusted sources:**

| Entry point | Checked against the auth ID? | Effect |
|---|---|---|
| `POST /ras-api/file-processing/status/:userId` (path) | **No**: the route is unauthenticated | Used as the `fileSessions` key, the GridFS `metadata.userId`, the DES `pensionSchemeOrganisationID` for bulk lookups, and audit `userIdentifier` |
| `POST /create-file-session` (body `userId`) | **No** | Becomes the `fileSessions` key, which is created or overwritten |
| `GET/DELETE /get-file-session/:userId`, `/delete-file-session/:userId` | Yes (equality; 400 on mismatch) | Cache key |
| `DELETE /ras-api/file/remove/:name/:userid` | Ignored: the auth ID is used | — |

⚠️ **Observation:** the authorised ID (from the enrolment) and the ID actually used diverge in two places:

- **Bulk lookups**: DES receives the `userId` from the callback path. It is not authenticated at that point, and there is no authenticated user in the callback request.
- **File download and removal**: the auth ID is passed to the repository, but only for logging. The query filters only by `filename`.

**Uses**:
- DES payload `pensionSchemeOrganisationID`
- `fileSessions` cache id (`SimpleCacheId`)
- `FileSession.userId`
- GridFS metadata `userId`
- audit `userIdentifier` / `userId`
- log messages (logged deliberately in place of the NINO)

**Validation**: there is no format check locally, in a library or in a contract. No `PsaId` or similar wrapper is used.

## 3. Entity/file identifiers – Upscan reference and GridFS ObjectId

**Upscan `reference`**:
- **Issuer**: Upscan. The frontend initiates the upload and receives the reference.
- **Lifecycle**:
  1. It arrives in the callback body `reference`.
  2. It becomes the temp-file prefix (`Files.createTempFile(reference, ".csv")`).
  3. It becomes the GridFS `filename` and the `metadata.reference` / `metadata.fileId`.
  4. It is stored in the session as `userFile.reference` and `fileMetadata.id`.
  5. The frontend later uses it as `:name` in `getFile` and `remove`.
- It also appears in create-session bodies, where it is validated as non-empty and then discarded.

**Validation**: none, apart from the non-empty check on create-session.

**Rule mismatches and risks**:
- ⚠️ **Not bound to the owner.** `fetchFile` and `removeFile` query `{filename: name}` only, so knowing the reference is enough to download or delete another organisation's results. References are Upscan-issued UUIDs, which are hard to guess, but this is still an authorisation gap.
- ⚠️ The reference is used, unvalidated, as a `createTempFile` prefix. A value containing a path separator makes `createTempFile` throw `IllegalArgumentException` in `createFileWriter`. That call sits outside the `try` in `manipulateFile`, inside a `Future.onComplete`, so the error is swallowed and the session is never marked FAILED.
- ⚠️ The path `name` is interpolated into `Content-Disposition: attachment; filename="<name>"` without escaping quotes.
- ⚠️ `FileController.remove` treats `fileName` as an `ObjectId` when removing chunks. These are different identifiers, so the parse nearly always fails (see `dependencies.md`).

**GridFS `ObjectId`**:
- Generated by Mongo on upload and exposed as `ResultsFileMetaData.id` in the file session.
- Used internally by `fetchResultsFile`, by `removeChunk` (`files_id`) and by the orphaned-chunk clean-up.
- It is never accepted from callers, except in the faulty parse in `remove`.

## Party identifiers table

| Identifier | Frontend/API key(s) | Upstream key (DES residency status) | Local rule | Contract rule |
|---|---|---|---|---|
| NINO | `nino` (API JSON), CSV column 1 | `nino` | Case-insensitive regex, suffix optional; padded to 9 and upper-cased | v2: case-sensitive, suffix optional; v1: suffix required |
| First name | `firstName`, CSV column 2 | `firstName` | `^[a-zA-Z &`\-'^]{1,35}$`, non-blank; upper-cased | Same regex |
| Last name | `lastName`, CSV column 3 | `lastName` | as above | Same regex |
| Date of birth | `dateOfBirth`, CSV column 4 | `dob` (`yyyy-MM-dd`) | API: ISO only; CSV: 4 formats; strict; not in the future | `^\d{4}-\d{2}-\d{2}$` |
| Pension scheme organisation ID | (auth) / callback path `userId` | `pensionSchemeOrganisationID` | none | none |

**NINO normalisation algorithm**: `nino.padTo(9, ' ').toUpperCase`. Spaces inside the value are not removed. The regex is matched against `toUpperCase` of the raw input, before padding.

| Identifier | Format checked locally? | Checked against the authenticated user? | Encoded when put in a URL? |

## Recommendations

1. Bind results files to their owner: add `metadata.userId` to the GridFS filters in `fetchFile` and `removeFile`. Do the same for the session by dropping `userId` from the create-session body and using the auth-derived ID.
2. Derive the organisation ID with a single, deterministic helper used by every controller, with an explicit priority order of enrolment keys.
3. Authenticate or otherwise protect the Upscan callback, for example with an unguessable per-upload token in the callback URL, and allow-list the `downloadUrl` host.
4. Enforce the v1 NINO rule (suffix required) when `Accept` is v1, or document the leniency. Consider the `domain` library's `Nino` validation so the rule has one source.
5. Sanitise the reference before using it as a temp-file prefix, and escape it in `Content-Disposition`.
6. Pass the inbound `HeaderCarrier` to `DesConnector` so that the `CorrelationId` can be traced to the request.
7. Remove the `ObjectId(fileName)` chunk-deletion path in `FileController.remove`, or pass the real GridFS id from the session.
